== The .luhmann.ini file

Configuration is optional — Luhmann runs with sensible defaults.  To override
them, place a file named `.luhmann.ini` *inside your notes directory* (the same
directory you pass on the command line), not next to the binary.

[IMPORTANT]
====
The config file must live at `<notes-dir>/.luhmann.ini`.  A file placed
anywhere else (for example beside the executable) is silently ignored.  At
startup Luhmann prints which config file it loaded, or reports that none was
found and defaults are in use, so you can confirm it was picked up:

[source]
----
Luhmann starting
  root:        /home/me/Documents/second-brain
  config:      /home/me/Documents/second-brain/.luhmann.ini
  port:        2022
  bind:        127.0.0.1
  render-jobs: 12
  public:      target/public
----
====

The file is a simple `key = value` format.  Blank lines and lines beginning
with `#` or `;` are ignored.  Every key is optional; unspecified keys keep their
default.

[source,ini]
----
# ~/Documents/second-brain/.luhmann.ini
port            = 2022
bind            = 127.0.0.1
render-jobs     = 12
editor          = nvim-qt
catch-all-label = unfiled
asciidoctor     = /usr/bin/asciidoctor
luhmann-dir     = /home/me/Documents/second-brain/.luhmann
----

== Settings

[cols="1,1,1,3", options="header"]
|===
| Key | Type | Default | Meaning

| `port`
| integer
| `2022`
| TCP port the server listens on (plain HTTP).

| `bind`
| string
| `127.0.0.1`
| IPv4 address to listen on.  `127.0.0.1` keeps the server private to this
  machine; `0.0.0.0` listens on every interface; a specific address such as
  `192.168.1.50` binds just that interface, which is narrower than `0.0.0.0`
  where it is enough.  Host names are *not* resolved -- use a literal dotted
  quad.  An unparseable value is refused at startup rather than falling back,
  so a typo cannot present as "running but unreachable".  See
  <<network-exposure>>.

| `render-jobs`
| integer
| `8`
| How many `asciidoctor` processes to run in parallel during the initial
  build.  Higher values speed up start-up on multi-core machines, with
  diminishing returns past the physical core count.  See the README's
  "Startup performance" section.

| `editor`
| string
| _(unset)_
| Command used by the `e` shortcut / `/api/edit` to open a note, e.g.
  `nvim-qt` or `code -g`.  The note's path is appended as the final argument.
  If unset, the editor feature is disabled.  Also disabled automatically
  whenever `bind` is not loopback -- see <<network-exposure>>.  See
  <<editor-integration>>.

| `catch-all-label`
| string
| `unfiled`
| Tag applied to notes that declare no `:tags:`, so every note is reachable
  from `/tags`.

| `asciidoctor`
| string
| first `asciidoctor` on `PATH`, else `/usr/bin/asciidoctor`
| Path to the `asciidoctor` binary used for rendering.  When unset, the
  `PATH` is searched, so a Homebrew install (`/opt/homebrew/bin`) or a gem
  install is found without configuration.  The resolved path is printed at
  startup.

| `luhmann-dir`
| string
| `<notes-dir>/.luhmann`
| Where Luhmann keeps derived files (the render temp dir, etc.).  This
  directory is excluded from note enumeration.
|===

The static-asset directory (CSS/JS/graph page) is resolved separately, in this
order: the `LUHMANN_PUBLIC` environment variable, else `public` beside the
binary (the PasBuild layout, `target/public`), else `src/main/resources/public`
for in-repo development runs.

[[network-exposure]]
== Network exposure

Luhmann listens on `127.0.0.1` by default, reachable only from the machine it
runs on.  Serving it elsewhere -- a NAS, a home server -- means setting `bind`
to an address other than loopback:

[source,ini]
----
bind = 0.0.0.0        # every interface
bind = 192.168.1.50   # one interface only
----

Prefer a specific interface address over `0.0.0.0` where one suffices: it does
not expose the server on interfaces the host may acquire later.

=== What changes when you do this

Luhmann has *no authentication and no TLS*.  Any machine that can reach the
port can read every note.  Serve a non-loopback address only on a network you
trust, or place an authenticating reverse proxy in front of it and leave
Luhmann itself on loopback.

The startup banner states the exposure rather than leaving it to be
discovered:

[source]
----
Luhmann ready on 0.0.0.0:2022 (reachable from other machines; no authentication)
  /api/edit is disabled while bound off-loopback
----

=== Why /api/edit switches off

`GET /api/edit?note=<id>` launches the configured `editor` as a process on the
host.  That is a reasonable convenience on a private listener, and a remote
process-spawn primitive on a reachable one -- with nothing authenticating the
caller.  Luhmann therefore refuses the endpoint with `403` whenever `bind` is
not loopback, regardless of whether `editor` is set.

In practice this costs nothing: a host that binds an external address is
usually headless, with no display for an editor to open onto.  Edit notes on
the machine you are sitting at, over a loopback instance or a file share.

[[editor-integration]]
== Editor integration

Pressing `e` while viewing a note (or calling `GET /api/edit?note=<id>`) runs
the command from the `editor` setting with the note's absolute path appended as
the final argument.  The editor is launched as an independent process; Luhmann
does not wait for it.  After you save, the file watcher picks up the change and
the browser reloads automatically.

How you configure `editor` depends on whether your editor draws its own window
or needs a terminal:

=== GUI editors (simplest)

An editor that opens its own window works directly, because it does not need a
controlling terminal:

[source,ini]
----
editor = code -g          # VS Code (-g so a path argument opens that file)
editor = gvim             # GUI vim
editor = nvim-qt          # GUI neovim
editor = kate             # KDE
editor = gedit            # GNOME
----

=== Terminal editors (need a terminal wrapper)

Console editors such as `vim`, `nvim`, `mcedit` and `nano` draw their UI on a
terminal.  Launched on their own they have no terminal to draw on, so the
process starts but nothing appears.  Wrap the editor in a terminal emulator —
no shell script is required, the `editor` command simply *is* the terminal
launching the editor:

[source,ini]
----
editor = gnome-terminal -- mcedit   # GNOME Terminal (modern '--' syntax)
editor = gnome-terminal -- vim
editor = konsole -e mcedit          # KDE Konsole
editor = xterm -e vim               # xterm
editor = kitty mcedit               # kitty
----

Because the note path is appended as the last argument, `gnome-terminal -- vim`
becomes `gnome-terminal -- vim /path/to/note.adoc`, i.e. a terminal window
running the editor on that file.

[NOTE]
====
The `editor` value is split on spaces, so an executable or argument that itself
*contains* a space (for example a path with a space in it) is not currently
supported.  Prefer the `gnome-terminal -- <editor>` form over the deprecated
`gnome-terminal -e "<editor>"` form, which also quotes awkwardly.
====

If `editor` is unset, the `e` shortcut is disabled and `/api/edit` returns
`400`.

=== macOS

==== VS Code

VS Code ships a command-line launcher inside the application bundle.  Expose it
on the `PATH` under a name without spaces, either with the VS Code command
*Shell Command: Install 'code' command in PATH* (which creates
`/usr/local/bin/code`) or with a symlink:

[source,shell]
----
ln -sf "/Applications/Visual Studio Code.app/Contents/Resources/app/bin/code" \
  ~/.local/bin/code
----

Then:

[source,ini]
----
editor = code
----

The symlink must target `Contents/Resources/app/bin/code`, the launcher script.
`Contents/MacOS/Code` is the application binary itself; invoking it directly
starts a separate application instance rather than opening the file in the
running one.  The full bundle path cannot be used as the `editor` value because
it contains spaces (see the note above).

==== Terminal editors

There is no macOS equivalent of `gnome-terminal -- vim`: Terminal.app does not
accept a command to run on its command line.  A small wrapper script asks
Terminal.app to open a new window running the editor.  Save it as, for example,
`~/.local/bin/luhmann-vim` and make it executable:

[source,shell]
----
#!/bin/sh
# Open the note in vim inside a new Terminal.app window.
exec osascript - "$1" <<'EOF'
on run argv
  tell application "Terminal"
    do script "vim " & quoted form of (item 1 of argv)
    activate
  end tell
end run
EOF
----

[source,ini]
----
editor = luhmann-vim
----

`quoted form of` passes note paths containing spaces or quotes through intact.
Substitute `nvim`, `mcedit` or another console editor for `vim` as required.
macOS may ask, on first use, for permission to control Terminal.app.

==== Executable lookup

A bare command name such as `code` or `luhmann-vim` is resolved on the `PATH`
that Luhmann inherited when it was started.  A server started from an
interactive shell sees that shell's `PATH`; one started by launchd does not
include `~/.local/bin`.  In the latter case give the absolute path, for example
`editor = /Users/me/.local/bin/code`.
